WorldgenD

Doing ethically questionable things to speed up Minecraft world generation.

WorldgenD runs Mojang's own server code, headless, and makes vanilla world generation finish sooner: 6.80–6.94 ms per chunk on our 6,400-chunk benchmark.

View on GitHub See the benchmarks

Not a terrain generator. Iris and its relatives design new worlds; WorldgenD takes the world Mojang already ships and generates it faster.

Against Paper

Paper's chunk system also runs generation steps in parallel. Stock Paper uses 2 worker threads on this box. Give it 7 and it becomes a very different server, so this page always says which Paper it means.

The last interleaved race (3 rotated rounds) put Orion v5 and 7-worker Paper inside one noise band. The servers also tick and write chunks to disk, which WorldgenD did not, so read that as parity, not a win.

Orion v5.7 has not been raced against Paper yet. Until that race is run and published, we claim no margin over 7-worker Paper.

The evolution of WorldgenD

Every scheduler from the mosaic to Orion v5.7. Effective ms per chunk at 6,400–9,216 chunks, 7 workers unless noted. Rows come from different sessions, which drift 7–10%, so small gaps between neighbours mean little.

  1. Mosaic

    Politely lying to Mojang.

    WorldgenD never starts a Minecraft server. It assembles just enough of one to build a real world, then asks it for chunks. The server, having no idea it was never turned on, obliges.

    The jar's own bytecode says no generation step looks further than 8 chunks. So chunk space is tiled into 256 phases at modulus 16, and every chunk in a phase is guaranteed independent of the others.

    35.17 ms per chunk #26

  2. Orion v1

    A demand-driven scheduler with an area lock, dispatching from one thread. It was slower than the mosaic it was meant to replace, and the reason was useful: getChunkFuture() blocks when called from the main thread. Measured at 4 workers.

    45.04 ms per chunk #24

  3. Orion v1.1

    Multi-threaded dispatch, built on that finding. It reported zero failures and was badly wrong: 64 chunks in flight where the geometry allowed one. Never timed at full scale.

    Not timed at full scale #25

  4. Orion v2

    One scheduler thread decides, worker threads just generate. The first real win in the Orion line: 24–27% faster than the mosaic.

    25.78 ms per chunk #26

  5. Orion v2.1

    Not a new architecture, just less wasteful.

    v2 rescanned the whole backlog after every finished chunk. A JFR profile put that scan at 32.4% of all CPU time in the run.

    v2.1 buckets chunks into a spatial grid once, then checks only the neighbourhood of each finished chunk. The scheduler's share fell to 1.03%.

    20.77 ms per chunk #30 #33

  6. Orion v2.2

    Hands chunks out in scattered order, restoring a property the mosaic had for free. Same throughput, roughly half the median latency.

    20.72–20.92 ms per chunk #35 #42

  7. Orion v3

    Multi-threaded admission. It deadlocked inside vanilla's own task polling; a two-method bytecode patch fixed it. Parity with v2.1: a correctness fix, not a speedup.

    19.71–20.87 ms per chunk #44 #49

  8. Orion v3.1

    Memoizes a biome predicate in surface rules. The cost it removed was real and too small to see: +0.8%, a null result.

    20.39 ms per chunk #53

  9. Orion v4

    Ports C2ME's fix for structure generation's thread-safety races. Costs nothing measurable, and it is what made parallel structure steps possible later.

    20.68–20.80 ms per chunk #56 #62

  10. Orion v5

    The ceiling was one lane wide.

    Vanilla sends surface, carvers, features and structures for the whole world through a single executor, one chunk step at a time. Four findings had blamed "dependency scarcity" for what was really that lane.

    v5 patches one method so those steps run on the worker pool under area locks. CPU use went from about 313% to 709% of a possible 800%, and total time fell 59.5%.

    8.16–8.65 ms per chunk #62

  11. Orion v5.1

    SIMD density batches. Real in the microbenchmark, invisible at full scale.

    7.77–8.25 ms per chunk #66

  12. Orion v5.2

    An optimized Perlin noise port removes the hottest lookup method. Total generation time: a statistical tie.

    8.05–8.40 ms per chunk #67

  13. Orion v5.3

    Four allocation-pressure fixes from a JFR profile. Bit-exact and fewer GCs, but no confirmed throughput win.

    7.87–9.34 ms per chunk #68

  14. Orion v5.4

    C1GC, a bounded chunk-reclamation pipeline. It fixes a real hang and out-of-memory at 65,536 chunks, at a cost of about 6% at 6,400.

    8.66–9.17 ms per chunk #69

  15. Orion v5.5

    C1GC reclaims only under heap pressure and on the right thread, fixing a v5.4 race. Bundles the v5.1 and v5.2 kernels. About 12% faster than v5.4.

    8.10 ms per chunk #70

  16. Orion v5.6

    Admits 16 chunks at a time and triggers C1GC earlier. Median chunk latency down 76%, p99 down 57–70%. Total time at parity.

    7.87 ms per chunk #73

  17. Orion v5.7

    Arithmetic, done in bulk.

    With the lane gone, generator math is the bottleneck. v5.7 fills density cells in whole arrays, updates interpolators only when read, and shares a surface cache across chunks.

    Three independent replications, an ablation, and two more blocks: 30 wins in 30 pairs, bit-exact output.

    6.80–6.94 ms per chunk #74

How it works

Mojang's generator does the generating. WorldgenD changes who waits for whom.

Parallel scheduling

Orion admits 16 chunks at a time into a bounded window and feeds 7 workers. A spatial index means a finished chunk only wakes its neighbours, so the scheduler costs about 1% of CPU instead of a third.

Runtime patching

WorldgenD's compiled code names no Minecraft class. A Java agent rewrites a few methods of the jar you supply as it loads: chunk steps move onto the worker pool under write-radius locks, and structures take one global lock. Every patch sits behind a flag.

C1GC

Vanilla keeps every chunk it hands back alive for the life of the JVM. At 65,536 chunks that heap only grows. C1GC releases finished chunks in bounded batches, and only when the heap is under pressure. It is a bouncer, not a garbage collector.

Batching

Density functions compute terrain one block at a time. v5.7 fills each 128-entry cell array per node in one loop, skips interpolators nobody reads, and caches surface height across chunks, with a 92% hit rate.

Version adapters

Every Mojang class is a string looked up at runtime, so a new Minecraft version means a new mapping, not a fork. Today WorldgenD targets the 26.1.1 server jar; adapters for other versions are not shipped yet.

Research, including the parts that failed

75 numbered findings and 366 filed runs, each with a CSV row, a profile, or bytecode behind it. A lab notebook that only records the wins is marketing.

How a result gets counted

Interleaved
Arms alternate inside one block and leg order rotates every round, so drift over time can't favour either side.
Replicated
A win needs a consistent 3–4% or better, repeated by a separate run from a separate source snapshot.
Bit-exact
Block-state histograms are hashed and diffed. "0 failed" is not a correctness check.
Filed
Every run goes into the CSVs and charts are regenerated from them, including runs that make us look worse.

Ideas that did not survive

  • Orion v1 45.04 ms per chunk, slower than the mosaic it was built to replace.
  • The first "we beat Paper" An interleaved rerun showed it was mostly a lucky draw.
  • Poll-gating the scheduler Two null results. The fix was to stop scanning, not scan less often.
  • SIMD, FFM, AOT cache, no structures Five misses at a ceiling that turned out to be a serial lane.
  • A density-function compiler 23–27% slower once wired into real generation.
  • Six v5.7-era hypotheses All bit-exact, none consistent enough to ship.

Open source, and staying that way

The generator is meant to stay open source. Nothing of Mojang's ships in the repository: you bring the official server jar, and WorldgenD reads it at runtime. It is a remote control, not a copy of the TV.

It runs headless on whatever box you have spare. No network, no RCON, no tick loop. Java 25 and a server jar are the whole install. 

git clone https://github.com/Earth1283/WorldgenD
cd WorldgenD
# put the official server jar in servers/
./gradlew run
